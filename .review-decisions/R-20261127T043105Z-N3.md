## `src/ufa/src/commands/vouchers.rs` — `vouchers delete <id>` gives no context for a success answer that ufa cannot read

**Settled** 2026-11-27 (branch ufa, finding R-20261127T043105Z#N3)

The finding is correct. `delete_voucher` passes a `FailedAnswer::Unreadable`
error through with no context. `create_vouchers` and the filtered deletion say
that the controller can have acted on such an answer. For
`ufa vouchers delete <id>`, the user reads only that the API answered HTTP 200
and that ufa could not read the whole body.

The command exits with an error, thus the user knows that ufa did not confirm
the deletion. A second run is harmless, because it gets a 404 when the voucher
is gone. A fix adds a `failed_answer` match and a test of the message. That fix
is new code for a review to read, and it starts one more review cycle for one
unclear message.

**The boundary.** A `vouchers delete <id>` that reports a success, or exits 0,
on an answer that ufa could not read is a new occurrence. The text of this
error is settled.
