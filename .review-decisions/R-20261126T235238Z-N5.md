## `src/ufa/src/client.rs` — the `--insecure` advice shows also when `--insecure` is on

**Settled** 2026-11-26 (branch ufa, finding R-20261126T235238Z#N5)

The finding is correct. `handle_request_error` does not know if certificate
verification is off. `is_tls_failure` cannot tell a refused certificate from a
different handshake failure, as its doc says. Thus a handshake that fails for a
different reason, for example a plain HTTP host on an `https` URL, tells the
user to use `--insecure` also when the user gave `--insecure`.

The advice is wrong only in that case, and the error text of reqwest that the
message holds still names the real cause. A fix keeps a new field in
`UnifiClient`, changes each constructor and each test that builds a client,
and adds a test with a server that refuses the handshake with verification
off. The cost is larger than the defect, which is one line of advice that the
user can ignore. `.review-decisions/R-20261125T160218Z-N1.md` settles the
words of that advice.

**The boundary.** An advice that tells the user to turn verification off when
the cause is not TLS at all, for example a refused connection or a timeout, is
a new occurrence. The advice for a TLS handshake failure with `--insecure`
already on is settled.
