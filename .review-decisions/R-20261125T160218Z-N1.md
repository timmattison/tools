## `src/ufa/src/client.rs` — the TLS advice writes `--insecure` with no value

**Settled** 2026-11-25 (branch ufa, finding R-20261125T160218Z#N1)

The finding is accurate. `handle_request_error` tells the user to "Use the
--insecure flag". The flag is `Option<bool>` with
`value_parser = parse_bool_env` and no `default_missing_value`
(`src/ufa/src/main.rs`), thus it takes a value. `ufa --insecure sites` reads
`sites` as that value and fails with `Invalid boolean value: sites`. The README
writes the correct form, `ufa --insecure true sites`.

**The cost is a new review cycle.** This round of the review loop is
record-only. A change to the advice is new text in an error, and the finding
also asks for a new test that parses the advice as a command line. A fresh
review reads both and can find a new nit. Then a new fix round starts, and the
loop does not end clean. The harm is small:

- The second line of the same advice, `UNIFI_INSECURE=true` in the `.env`
  file, works as written.
- The clap error for a bad value names the flag with its value,
  `--insecure <INSECURE>`, and it lists the accepted values
  (`Use true/false, 1/0, yes/no, or on/off`). Thus a user who types the flag
  with no value gets the correct form from the next error.

**The boundary.** This decision settles only the words of the `--insecure`
line in the TLS advice of `handle_request_error`. A different place that
tells the user to type `--insecure` with no value is a new finding.
