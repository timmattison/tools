## `src/nle/src/filters/redaction/stream.rs` `osc_text` — no test holds that the `;` after the OSC number is not text

**Settled** 2026-11-27 (branch issue-156, finding R-20261127T005018Z#N1)

The finding is accurate. The tests of the OSC number search for digits and for
`0`, and no search matches a `;`. A mutant of `osc_text` that returns
`payload.start + digits..payload.end` puts the `;` into the text, and each test
passes. With that mutant, a search for `;` turns `ESC ] 0 ; title` into
`ESC ] 0 X title`.

The code is correct. `osc_text` returns `payload.start + digits + 1..payload.end`,
and its doc comment states the rule. The test
`the_number_of_an_osc_sequence_is_not_searched` holds the number itself. The
gap is in the tests, not in the behavior that a user gets.

The fix costs more than the gap. The branch is in the record-only round of the
review loop. A new test is new code that a fresh review must read, and a nit in
that code starts one more fix round. Thus the loop does not end clean.

The boundary: this record settles the test of the `;` after the OSC number
only. A change to the start of the text range in `osc_text` is a new finding. A
search that changes the `;` after the number of a real sequence is a new
occurrence, and it reopens this decision. A test such as
`one("\x1b]0;a;b\x07", ";", "X") == "\x1b]0;aXb\x07"` closes this decision.
