## `src/nle/src/types.rs` — a save to a symlink replaces the link

**Settled** 2026-11-24 (branch 170, finding R-20261124T194019Z#N4)

`Recording::save` renames a temp file over `path`. When `path` is a symlink,
the rename replaces the link with a regular file, and the target keeps its old
content. The `File::create` save that c9acf8fe replaced wrote through the link.
`std::fs::metadata(path)` follows the link, thus the new file gets the mode of
the target.

The finding is accurate. It is not fixed, because:

- **The replace is the design of the save.**
  `test_save_replaces_an_existing_file_instead_of_writing_into_it` holds the
  same rule for a hard link. A save that follows a symlink is a different rule,
  and a person must choose it.
- **The mode of the target is the applicable mode.** The data of the recording
  has one mode, and that mode is on the target, not on the link.
- **The app does not send a symlink to the save today.** `load_recording`
  canonicalizes the path, thus `metadata.file_path` names the target. The
  frontend calls no save command yet.
- **The round is record-only.** The fix resolves the last part of `path` before
  the save. It changes the rule of the save, it needs new tests, and it starts
  a new review cycle.

The boundary: a save from the frontend to a path that does not come from
`metadata.file_path`, or a report of a link that a save replaced, reopens this
decision.
