## `src/hexfind/src/main.rs` — the order of the red and green commits of the broken-pipe fix stays as it is

**Settled** 2026-11-24 (branch issue-731, finding R-20261123T232226Z#N1)

The review found that the green commit `b4b12c87` changed the 11 `unwrap()`
calls of `display_hex_dump` to `?`, but the red commit `aa12304a` before it
does not ask for that change. Its CLI test closes the pipe before the first
write, thus the run stops at the header and never reaches a hex dump. The test
of the writes of the hex dump came after the green, in `4110c0e2`.

The finding is accurate. The order breaks the rule that a failing test comes
before the code that it asks for.

**The only fix is a rewrite of the history, and it costs more than the
defect.** The three commits are on `origin/issue-731`, the head of PR #735. A
new order needs an interactive rebase and a force push, and the git guardrail
of this machine refuses a force push. The coverage is real: the body of
`4110c0e2` records a mutant (an `unwrap` on the last write of a hex dump line)
that its test fails. This repository squash-merges each PR, thus the three
commits do not reach `main` as separate commits. The reviewer also said not to
rewrite the branch for the order alone.

**The boundary.** This decision settles the order of the commits `aa12304a`,
`b4b12c87`, and `4110c0e2` only. It does not settle a missing test: a write of
`print_matches` or `display_hex_dump` whose error no test reaches is a new
finding. It does not let a later green commit, on this branch or on a
different branch, add code that its red test does not ask for.
