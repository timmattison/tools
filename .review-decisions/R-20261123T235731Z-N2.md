## `src/gitrdun/src/stats.rs` — the order of the red and green commits of the saturating count stays as it is

**Settled** 2026-11-24 (branch issue-731, finding R-20261123T235731Z#N2)

The review found two green commits that add code that their red commit does
not ask for:

1. The hexfind pair `aa12304a` and `b4b12c87`. The earlier finding
   R-20261123T232226Z#N1 reported the same pair, and
   `.review-decisions/R-20261123T232226Z-N1.md` settles it. This file does not
   settle it again.
2. The gitrdun pair. The green commit `76b51bc2` changed `self.count += 1` to
   `self.count.saturating_add(1)` in `GitOpStats::record`, but the red commit
   `3164117b` before it records only two operations, thus the count never
   comes near `u64::MAX`. The test of the count came after the green, in
   `01d17dd9`.

The finding is accurate. The order breaks the rule that a failing test comes
before the code that it asks for.

**The only fix is a rewrite of the history, and it costs more than the
defect.** The three gitrdun commits are on `origin/issue-731`, the head of
PR #735. A new order needs an interactive rebase and a force push, and the git
guardrail of this machine refuses a force push. The coverage is real: the body
of `01d17dd9` records a mutant (`self.count += 1`) that its test fails with the
panic "attempt to add with overflow". This repository squash-merges each PR,
thus the three commits do not reach `main` as separate commits. The reviewer
also said not to rewrite the branch for the order alone.

**The boundary.** This decision settles the order of the commits `3164117b`,
`76b51bc2`, and `01d17dd9` only. It does not settle a missing test: a branch of
`GitOpStats::record` or `GitOpStats::average` that no test holds is a new
finding. It does not let a later green commit, on this branch or on a
different branch, add code that its red test does not ask for.
