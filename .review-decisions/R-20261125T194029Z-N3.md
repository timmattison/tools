## `src/msgs/src/cache.rs` — `fill` reads the total and the rows of chat.db in two snapshots

**Settled** 2026-11-25 (branch msgs, finding R-20261125T194029Z#N3)

The finding is accurate. `Cache::fill` reads `COUNT(*)` in one statement, and
it scans the rows in a second statement. Each statement on `chat_db` is its own
read transaction. Thus a message that Messages writes between the two reads
makes `count` larger than `total`. `indexingProgress` in
`frontend/src/cache-status.ts` does not clamp the percent.

The effect is small:

- The window is the time from the end of the count to the first row of the
  scan. Only a prepared statement and one progress event are in that window.
- `indexingProgress` rounds down. Thus the percent is more than 100 only when
  the new messages are 1% or more of the total, for example 100 messages for a
  total of 10,000, all in that window.
- The wrong number shows only until the build ends. The index holds each row
  that the scan read.

The cost of a fix: a read transaction on `chat_db` around the two reads, or a
clamp in `indexingProgress`, each with a test. Each fix is new code for one
more review round, for a number that can be wrong during one build.

The boundary: a percent above 100 in the text of the index build is this
decision. These changes reopen it:

- Code uses `indexed` and `total` for more than the percent text, for example a
  bar width or a test for the end of the build.
- A slow step goes between the count and the scan.
- A user sees a percent above 100.
