## Commit order on a pushed branch — fork log tests of `crap` came after their green commits

**Settled** 2026-10-30 (branch issue-615, finding R-20261030T110703Z#N1)

The review found that some behaviors landed in a green commit before a test that
could fail for them. The review named the commits by the SHAs that they had
before a rebase. The commits on the branch now are these:

- The green commit `76ff6d54` ("--here adds a line to the fork log") also added
  the `fork-at` log call in `run_resume` and the warning of `log_fork`. Their
  tests came after it, in `dc22164f` (`cross_user_fork_adds_a_fork_at_line`) and
  `b7487d76` (`an_unwritable_log_warns_and_the_fork_starts`).
- The green commit `e768415d` ("append one record as one line") added
  `O_APPEND`, the mode `0600`, and the check for a short write. Their tests came
  after it, in `c185501d`.
- The test commit `414a1236` came after `ed8e5026`, which already read only the
  top-level keys of a line.

The bodies of those test commits say that the tests pass at once. The TDD rule in
`CLAUDE.md` asks for the red commit first. The finding is accurate.

It is not fixed, because the defect is the order of the commits and nothing else.

**The coverage is real.** The bodies of `c185501d` and `414a1236` name a mutant
that fails their tests. The run of `address-issues` for this finding did six
mutants on `cccfdc07`, one at a time. The file was restored after each mutant,
and `git status --short` was empty at the end.

- M1: the `log_fork` call in the cross-user branch of `run_resume` removed.
  `cross_user_fork_adds_a_fork_at_line` fails at `src/crap/tests/fork_log.rs:78`,
  because the fork log does not exist.
- M2: `ForkKind::ForkAt` changed to `ForkKind::Here` in that call. The same test
  fails at `src/crap/tests/fork_log.rs:185`, on `line["kind"] == "fork-at"`.
- M3: the error of `append_fork_record` in `log_fork` ignored with no warning.
  `an_unwritable_log_warns_and_the_fork_starts` fails at
  `src/crap/tests/fork_log.rs:151`, because stderr has no warning.
- M4: `exit(1)` added after that warning. The same test fails at
  `src/crap/tests/fork_log.rs:145`, because the fork does not start.
- M5: `.append(true)` changed to `.write(true).truncate(true)` in
  `append_fork_record`. Three tests of `fork_log::tests` fail, among them
  `two_appends_give_two_lines_in_order` and `concurrent_appends_never_mix_lines`.
- M6: the mode `0o600` changed to `0o644`. `new_log_file_has_mode_0600` fails.

What TDD gives, a test that can fail for the behavioral reason, is present. Only
the order of the commits is wrong.

**The one fix is a rewrite of pushed history, and it buys nothing durable.** The
finding says that the branch is not pushed. It is: `origin/issue-615` is at
`c7cb716b`, and PR #619 (branch issue-615) is open. A red-first order needs
`76ff6d54` and `e768415d` split, and every later commit gets a new SHA. The tool
is an interactive rebase, which only Tim can run. The next push then needs a
force push, which `block-dangerous-git.ts` refuses with no override. The review
`R-20261030T110703Z` ends on `c7cb716b`, thus after a rewrite
`pr-merge-gate.ts` calls the review `rewritten` and refuses the merge until a
fresh review of the whole branch. Against that: this repository squash-merges
every PR with an explicit `--subject` and `--body`, so no commit of this branch
reaches `main`.

**The boundary.** This decision settles the order of the named commits on the
branch `issue-615` only, where each test exists and a mutant shows that it can
fail. It does not settle a missing test, or a test that nobody showed can fail.
It does not permit a green commit that implements more than its red test asks
for, as a habit.

**The pattern.** This is the ninth branch with this shape (see the records of
`R-20261017T222526Z-N1`, `R-20261018T041353Z-N1`, `R-20261018T170445Z-N1`,
`R-20261018T235403Z-N1`, `R-20261020T163846Z-N1`, `R-20261022T182813Z-N1`,
`R-20261025T160203Z-N1`, and `R-20261028T194028Z-N1`). The repair belongs to the
brief of the green step in the TDD skills of the dotfiles repository
(timmattison/dotfiles issue #22), and not to this record.
