## Commit order on an unpushed branch — eight page-key guards of `krt` came after their green commits

**Settled** 2026-10-28 (branch issue-613, finding R-20261028T194028Z#N1)

The review found that eight test commits passed when they were written:
`b580718e`, `a2f8b2b8`, `4a816024`, `27db07d2`, `decbcfd4`, `d6dc3100`, `543b14a8`,
and `6fb63ace`. The green commit `324c858f` already held four rules that its red
test `2f75a23f` did not ask for: the clamp at the last full window, the
`room >= 3` rule, the store-back of the first row in `Table::draw`, and the read of
a fresh frame at each press in `apply`. The green commit `42ba5c14` already held
the top-page rule of Page Up. The TDD rule in `CLAUDE.md` asks for the red commit
first. The finding is accurate.

It is not fixed, because the defect is the order of the commits and nothing else.

**The coverage is real.** The body of each of the eight commits names a mutant and
says that the test failed under it. The run of `address-issues` for this finding
did four of those mutants again on `9edf8110`, with
`cargo test -p krt --bin krt live::` (69 tests pass with no mutant):

- With `let first = first;` in place of `let first = first.min(last);` in `fitted`,
  six tests fail: `the_top_of_a_fit_is_the_line_of_the_first_shown_row`,
  `hiding_the_list_of_the_keys_stops_the_scroll_at_the_last_full_window`,
  `the_help_key_keeps_the_first_row_of_the_scroll`,
  `page_down_stops_at_the_last_full_window`,
  `page_up_scrolls_back_by_the_page_that_page_down_took`, and
  `the_last_full_window_draws_an_image_on_each_of_its_rows`.
- With `room >= 2` in place of `room >= 3` in `fitted`,
  `a_window_too_short_for_a_scroll_ignores_the_page_keys` fails.
- With the line `self.first = drawn.rows.start;` removed from `Table::draw`,
  `the_help_key_keeps_the_first_row_of_the_scroll` and
  `the_reset_key_takes_the_scroll_back_to_the_first_row` fail.
- With `1` in place of `0` in the `up:` expression of `Pages` in `fitted`,
  `page_up_after_page_down_shows_the_first_frame_again` and
  `page_up_on_the_first_frame_changes_nothing` fail.

What TDD gives, a test that can fail for the behavioral reason, is present. Only
the order of the commits is wrong.

**The fix is a rewrite that buys nothing durable.** The branch is not pushed, so a
rewrite needs no force push, and that part of the argument of
`R-20261025T160203Z-N1` does not apply here. The rest of it does. A red-first order
needs `324c858f` and `42ba5c14` split into one green step for each guard. Those
steps are code that never existed, written only to make the history read red
first, and each one needs its own run of the tests. The tool is an interactive
rebase, and only Tim can run one. The review `R-20261028T194028Z` ends on
`77e21636`, thus after a rewrite `pr-merge-gate.ts` calls the review `rewritten`
and asks for a fresh review of the whole branch. Against that: this repository
squash-merges every PR with an explicit `--subject` and `--body`, so no commit of
this branch reaches `main`.

**The boundary.** This decision settles the order of the eight named commits on the
branch `issue-613` only, where each test exists and a mutant shows that it can
fail. It does not settle a missing test, or a test that nobody showed can fail. It
does not permit a green commit that implements more than its red test asks for, as
a habit.

**The pattern.** This is the eighth branch with this shape, and the first outside
`ha` (see the records of `R-20261017T222526Z-N1`, `R-20261018T041353Z-N1`,
`R-20261018T170445Z-N1`, `R-20261018T235403Z-N1`, `R-20261020T163846Z-N1`,
`R-20261022T182813Z-N1`, and `R-20261025T160203Z-N1`). Seven records settled the
order on their own branches, and none of them changed how a green commit gets
written. The repeat points at the brief of the green step and not at any branch: a
green subagent that sees the whole feature implements the whole feature. The
repair belongs to the skills that write that brief, which live in the dotfiles
repository, and not to this record.
