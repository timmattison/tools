## Commit order on a pushed branch — two green commits of `cctop` held rules that their red tests did not ask for

**Settled** 2026-11-16 (branch issue-697, finding R-20261116T114306Z#N1)

The review found two green commits that implement more than their red tests ask for. The SHAs below are the SHAs after the rebase of the branch onto `main`. The SHAs that the review named are in parentheses.

- The green commit `4827dad4` (`9a77c59d`), "add a new session to the board", added `LOG_CAPACITY`, the cap in `Board::record`, and the newest-first order of `Board::changes`. Its red commit `d4fe69a9` (`ac56d848`) tests none of them. The test came later, in `f12a636a` (`9d8213be`).
- The green commit `b6658055` (`930ca56c`), "focus a session in Zellij", added the path of `candidate_ttys` outside Zellij and the loop over more than one client. Its red commit `4c858bf4` (`d1d5833a`) tests only one client in Zellij. The two tests came later, in `547a3c29` (`f3b9f88f`).

The TDD rule in `CLAUDE.md` asks for the red commit first. The finding is accurate.

It is not fixed, because the defect is the order of the commits and nothing else.

**The coverage is real.** The run of `address-issues` for this finding applied each mutant below to `4b868d3e`, ran `cargo test -p cctop`, and then removed the mutant. With no mutant, all tests pass.

- With the loop that drops the oldest change removed from `Board::record`, 1 test fails: `board::tests::the_log_keeps_at_most_log_capacity_changes_and_drops_the_oldest`.
- With `self.log.iter()` in place of `self.log.iter().rev()` in `Board::changes`, 3 tests fail: `board::tests::changes_give_the_newest_first`, `board::tests::the_log_keeps_at_most_log_capacity_changes_and_drops_the_oldest`, `ui::tests::the_log_shows_at_most_eight_lines_with_the_newest_first`.
- With an `Err` in the `else` arm of `candidate_ttys` (the path outside Zellij), 2 tests fail: `focus::tests::a_focus_outside_zellij_reads_the_tty_of_the_target_and_skips_step_1`, `focus::tests::a_target_with_no_tty_outside_zellij_is_a_step_2_error`.
- With `.take(1)` on the clients of the Zellij server in `candidate_ttys`, 1 test fails: `focus::tests::the_first_client_with_a_wezterm_pane_gets_the_request`.

What TDD gives, a test that can fail for the behavioral reason, is present. Only the order of the commits is wrong.

**The fix is a rewrite that buys nothing durable.** The branch is pushed, and PR #700 (branch issue-697) is open. A red-first order needs each of the two green commits split into one green step for each rule. Those steps are code that never existed, written only to make the history read red first. The rewrite then needs a force push, and only Tim can run one. The merge gate then asks for a fresh review of the whole branch. Against that: this repository squash-merges each PR with an explicit `--subject` and `--body`, thus no commit of this branch reaches `main`.

**The boundary.** This decision settles the order of the commits named above on the branch `issue-697` only, where each late test exists and a mutant shows that it can fail. It does not settle a missing test, or a test that nobody showed can fail. It does not permit a green commit that implements more than its red test asks for, as a habit.

**The pattern.** Other branches have the same shape. See `R-20261028T194028Z-N1` and the records that it names. That record points the repair at the brief of the green step, in the skills of the dotfiles repository, and not at a branch.
