## `src/nle/src/filters/fast_forward/tests.rs` — the bad-option tables assert only the kind of the filter

**Settled** 2026-11-27 (branch issue-162, finding R-20261127T140646Z#N1)

The finding is accurate. `bad_options_fail_the_run` and
`bad_summary_options_fail_the_run` assert only that the render error holds
`KIND`. The pipeline writes `filter "{kind}" failed: {message}` itself
(`src/nle/src/pipeline.rs`), thus each case of the two tables passes also when
`mode_from` or `line_count_from` drops the name of the option. Only
`a_speed_of_one_or_below_names_the_option_and_the_reason` holds the claim that
the error names the option.

**The fix costs more than the defect in this round.** Each case of the two
tables already proves the behavior that matters to a user: a bad option stops
the run with a render error, and the run gives no output. Each message in
`mode_from` and `line_count_from` puts the name of the option in a
`format!` string that a person reads in the same function. A regression that
drops a name changes the text of an error, not what the filter does to a
recording.

The fix is a change of two test tables. A review reads that change, thus the
fix starts one more review cycle. This round of the review loop is
record-only.

**The boundary.** This record settles only the assertion on the name of the
option in the error text of these two tables. Each of these occurrences
reopens it:

- a case of either table that passes when the filter does not fail, or when it
  fails with an error that is not a render error
- a new option of the fast-forward filter whose bad value no test makes fail
- a change of `mode_from` or `line_count_from` that removes the name of the
  option from a message
- a statement in a file of the repository that says these two tables prove the
  name of the option
