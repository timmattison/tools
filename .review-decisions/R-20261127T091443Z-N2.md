## `src/wdid/tests/shell-definitions.rs` doc of `the_key_command_lines_give_the_command_of_each_key` — it states the old decode rule

**Settled** 2026-11-27 (branch issue-728, finding R-20261127T091443Z#N2)

The finding is accurate. The doc comment of the test says that the command
loses one level of backslashes. Since fde9ffa70, `read_key_command_line` in
`src/wdid/src/starts.rs` decodes each escape of readline through
`decode_key_command`, and its own doc says so. The test
`the_key_command_lines_decode_the_escapes_of_readline` holds the new rule.

The test itself is correct. The commands of its inputs hold only `\\` and `\"`
escapes, and the new decoder gives the same result for those escapes as the
old rule. The keys keep their `\C-` escapes, because the key stays as bash
writes it. Thus the
stale sentence changes no test result. The fix is prose in a test file, and
the branch is in a record-only round of its review loop. A changed comment is
new text that a fresh review reads, and that review can find a new nit in it.
That starts a new fix round for a comment that changes no result.

The boundary: this decision settles the doc comment at
`src/wdid/tests/shell-definitions.rs:1902-1905`. A change to the inputs of
that test that puts an escape other than `\\` and `\"` into a command reopens
this decision,
and that change corrects the sentence in the same commit.
