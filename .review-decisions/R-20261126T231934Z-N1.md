## `src/nle/src/pipeline.rs` `InPlaceFilterFn` — step 4 says the end stays, but a region after the end can raise it

**Settled** 2026-11-26 (branch issue-168, finding R-20261126T231934Z#N1)

The finding is accurate. Step 4 of the doc of `InPlaceFilterFn` says that the
end of the timeline stays. For a region that starts after the end, the code
lets the end grow. Take events at 0 s, 1 s, and 4 s, and a range from 5 s to
6 s. Then `top` is 5 s and the length of the view is 0. An in-place filter that
answers one event at 0 passes the check `0.0..=view.length`. That event lands
at 5 s, and `*end = end.max(last_time(&result))` raises the end from 4 s to
5 s.

The code is correct, and the doc is incomplete. The end of the timeline must
not come before the last event, and the code keeps that invariant. For each
region that starts at or before the end, the ceiling is at or before the end,
thus the end stays as step 4 says. No shipped filter gets to the other case:
the cursor filter answers nothing for a region with no events that is open or
has the length 0 (`src/nle/src/filters/cursor.rs`, `Rewriter::run`).

**The fix costs more than the defect in this round.** One fix is prose in
step 4. A different fix refuses such an answer, which is a new rule and a new
error. Both need a new test of the 5 s to 6 s case. This round of the review
loop is record-only. A change of code or of a document starts one more review
cycle, and that review can find a new nit in the new text.

**The boundary.** This record settles only the case of a region that starts
after the end of the timeline. Each of these occurrences reopens it:

- a shipped filter that answers an event for a region that starts after the
  end
- the end of the timeline grows for a region that starts at or before the end
- an event after the region moves because of an in-place filter
