## `src/ufa/src/http.rs` `parse_body` — the source error can quote a whole JSON string of a success answer

**Settled** 2026-11-27 (branch ufa, finding R-20261127T145031Z#N1)

The finding is accurate. `parse_body` cuts the body to
`ERROR_BODY_DISPLAY_CHARS` in its own message, but it keeps the
`serde_json::Error` as the source. `main` returns `Result<()>`, thus anyhow
prints the chain under "Caused by". When the body is valid JSON and holds a
string where the model expects a different type, serde writes the whole
string into that error (`invalid type: string "…", expected …`). The test
`a_huge_unparseable_body_is_quoted_only_in_part` uses a body that is not JSON,
thus it cannot fail on this path.

**The fix costs more than the defect in this round.**

- The defect needs a success answer of the controller or of the Site Manager
  API that holds a very long string in the wrong place. Neither API sends
  such an answer.
- The result is a long message on standard error. The command still fails,
  with the correct status. Nothing hangs, and the read limit of the body
  stays at 32 MiB.
- The body comes from the server. It holds no key of the user.
- The fix changes the error type and adds a test with a JSON string body.
  That code starts one more review cycle, and this round of the review loop
  is record-only.

**The boundary.** This record settles only the source error of `parse_body`
for a success answer that the APIs do not send. Each of these occurrences
reopens it:

- a path that quotes the whole body of an answer that the APIs do send, for
  example an error answer in the API error shape
- an error chain that prints a key, a token, or other secret of the user
- a new caller of `parse_body` that reads a body from a source other than the
  two APIs
