## `README.md`, `TLDR.md`, `src/workit/src/main.rs` — no text names the hidden-directory rule of the walk

**Settled** 2026-11-25 (branch workit, finding R-20261125T043207Z#N6)

The finding is accurate. The walk of `find_cargo_tomls` never enters a
directory below the search path whose name starts with a dot.
`a_package_inside_a_hidden_directory_is_not_found` in `tests/discovery.rs`
holds that rule. The README entry, the TLDR row, and the `--help` text of
`--exclude` and `--no-default-excludes` name only `target` and
`node_modules`. `--no-default-excludes` does not bring a hidden directory back.

It is not fixed, because the fix costs more than the defect:

- **The rule is intended.** A dot directory below the search path is almost
  always a tool directory, for example `.git`, `.cargo`, `.github`, or
  `.claude/worktrees`. A walk that entered them finds copies and caches, not
  packages of the tree.
- **A user can reach such a package.** The rule does not apply to the search
  path itself. Thus `workit --path .tools` lists each package below `.tools`.
- **The fix is prose in four places.** The README entry, the TLDR row, and two
  help texts get one more clause each. No behavior changes.
- **The cost is a new review cycle.** This round of the review loop is
  record-only. New text in four places is text that a review must read, and a
  fresh review can find a new nit in it. Tim chose to settle each nit with a
  record (decision H-742-2 on issue #742).

**The boundary.** This decision settles the documentation of the
hidden-directory rule. A change that makes the walk leave out a new kind of
directory with no documentation is a new finding. A change that makes the walk
leave out the search path itself when its name starts with a dot is a new
finding.
