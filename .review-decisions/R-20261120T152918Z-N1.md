## `src/gitnuke/src/branch_named.rs` — the question goes to stderr, but only stdin must be a terminal

**Settled** 2026-11-21 (branch issue-722, finding R-20261120T152918Z#N1)

The finding is accurate. `confirm` gives `ask` only `std::io::stdin().is_terminal()`, and `ask` writes the question to stderr. At a terminal with stderr sent to a file (`gitnuke issue-42 2>log`), gitnuke waits for an answer to a question that the person cannot see.

**Why it is not fixed.**

- The fix makes a case that works today fail. With `gitnuke issue-42 2>&1 | tee log`, stderr is a pipe, and tee shows the question on the terminal. If gitnuke also requires a terminal on stderr, that run refuses with exit code 10, and the person must add `--yes`. gitnuke cannot tell a pipe that a person reads from a file that nobody reads.
- The wait loses no data. Enter, any answer other than `y` or `yes`, and Ctrl-C all keep the worktree and the branch.
- `rm -i`, `cp -i` and `mv -i` put the question on stderr and read stdin with the same rule. gitnuke already refuses more than they do, because it refuses when stdin is not a terminal.
- The fix also needs a new pseudo-terminal run in `gitscratch::testing::pty` that puts stdin and stderr on the terminal, because the y and n tests of gitnuke put stderr on a pipe.
- The other suggested fix, a question on `/dev/tty`, is worse. A process with a controlling terminal but no terminal on stdin, for example a tool that an agent runs, then writes into the terminal of the person and waits.

**The boundary.** This record settles the wait when stdin is a terminal and stderr is not. It does not settle a question that gitnuke puts when stdin is not a terminal, or a nuke that goes on with no answer.
