## `MOSH_IMAGE_BUDGETS` — a stale value from a second mosh, and mosh is what closes it

**Settled** 2026-09-13 (branch issue-480, finding R-20260912T024123Z#I1)

The finding is accurate. `MOSH_IMAGE_BUDGETS` outlives the session that wrote
it. A tmux server or a Zellij server that a mosh session started hands the
whole environment of that session to every pane it opens later, and `tmux
update-environment` does not carry the `MOSH_*` names. So a reattach through a
second mosh leaves the caps of the first one in place. Where the second mosh
states a smaller Kitty cap, `ic` sends a transmission above it and mosh answers
`ENOSPC`. That is the empty screen this branch exists to prevent.

The process-tree gate proves that some mosh carries this session. It never
proves that this mosh is the one that wrote the variable.

**The repair belongs to mosh, and this repository cannot mint it.** A reader
can only compare two identities, and the variable states none. `ic` already
walks the process tree and reads the pid of the `mosh-server` that runs, so the
one missing half is the identity of the server that wrote the caps. mosh has to
write it. `timmattison/mosh-rs` issue 98 asks for that, at
<https://github.com/timmattison/mosh-rs/issues/98>.

**The repair that this repository can make alone is worse than the defect.** A
gate that refuses the caps until the variable names a pid refuses them for
every mosh that runs today, because no mosh writes a pid. Every session then
falls back to `PayloadBudget::MOSH`, and the branch buys nothing. Bounding a
stated cap by that careful number is the same answer with more code, because
raising the Kitty budget above that number is the whole point of the change.

**The boundary.** This settles the stale variable that a *second mosh* leaves
behind, and nothing else. It rests on three facts, and a new occurrence of any
one of them reopens it.

- The failure is loud. The Kitty path answers `ENOSPC`, so the user reads an
  error and not a wrong picture. A report of the Sixel path or the iTerm2 path
  cutting a picture in silence for this reason is a new occurrence.
- The failure needs a downgrade. It takes a second mosh that states a
  **smaller** cap than the first. A mosh that only raises a cap leaves a stale
  value under the real cap, which costs resolution and still draws.
- The failure needs a multiplexer that outlived the first session.

A further argument about the same hypothetical does not reopen this. A report
of a user who met it does.
