## `src/ufa/src/commands/vouchers.rs` — the warning that the controller can have made the vouchers is for an unreadable answer only

**Settled** 2026-11-27 (branch ufa, finding R-20261127T131122Z#N1)

The finding is correct. `FailedAnswer::Missing` (`src/ufa/src/http.rs`) also
holds a timeout or a reset that occurs after the POST went out. In that case,
the controller can have made the vouchers. The user then reads only
`Failed to send POST request: ...` from `handle_request_error`
(`src/ufa/src/client.rs`), and a second run can make duplicate vouchers.

The warning names `ufa vouchers list` only for `FailedAnswer::Unreadable`.
That case is certain: the controller sent a success status. `reqwest` does not
tell whether a timeout occurred before or after the body went out. Thus a
warning on `Missing` also shows for each connect timeout, where nothing went
out, and the warning then says something false in the common case. The cost of
the gap is one misleading message on a rare failure. A fix adds a new branch to
the error map and a new test, and it starts one more review cycle.

**The boundary.** A success status whose answer ufa cannot read, and that gets
no warning, is a new occurrence. A new create command (for example of a client
or a network) that has no warning for an unreadable answer is a new occurrence
too. The absence of a warning for `FailedAnswer::Missing` is settled.
