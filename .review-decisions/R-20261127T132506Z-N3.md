## `src/nle/src/filters/keystroke_hud/keys.rs` — `ESC ESC [ D` reads as Esc and Left, not Alt+Left

**Settled** 2026-11-27 (branch issue-161, finding R-20261127T132506Z#N3)

The finding is correct. rxvt, and iTerm2 with Option set to Esc+, send
`ESC ESC [ D` for Option+Left. `escape` reads the first `ESC` as Esc when the
next character is `ESC`, and the second `ESC` then starts `CSI D`. Thus the HUD
shows two boxes, `Esc` and `←`, and not `Alt+←`. The test
`escape_alone_and_doubled` holds only `ESC ESC`.

The two boxes are one correct read of the bytes. A press of Esc and then of
Left that reaches the recording in one read gives the same bytes. The reader
gives `Alt+←` for the xterm form `CSI 1;3 D`, and
`csi_cursor_keys_with_and_without_modifiers` holds that form. The fix is a new branch in `escape` and new
test cases. This round of the review loop is record-only. A code change is new
code that a review must read, and that review can start a new fix round.

Boundary: a change to the `ESC ESC` branch of `escape` reopens this decision.
A recording from such a terminal where the user asks for `Alt+←` reopens it
too. A new argument about the encoding does not.
