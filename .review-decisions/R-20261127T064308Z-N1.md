## `src/nle/src/filters/color_scheme.rs` `SlotStates::restore` — the restore writes the colors of the recording as written, also in the colon form

**Settled** 2026-11-27 (branch issue-166, finding R-20261127T064308Z#N1)

The finding is accurate. `follow` keeps the parameter text of the recording in
`SlotState::Set`, and `SlotStates::restore` writes that text. Thus a recording
that sets `38:2::1:2:3` in a range gets a restore of `ESC[38:2::1:2:3m`. The
module doc says "It always uses the semicolon form", and a reader can read that
sentence as a rule for each color that the filter writes. The sentence is in
the rule for each *new* color, and the README says "it writes each new color in
the semicolon form". The restore writes no new color. It writes the color of
the recording.

**The fix costs more than the defect.** The finding gives two fixes:

- A code fix: keep the semicolon form of the parsed color in `SlotState::Set`.
  The restore exists so that the text after the range has the colors that the
  recording gave it. If `termstate` misreads `38:2::1:2:3`, the recording
  without the filter gives that text the misread color. A restore in the
  semicolon form gives it a different color, thus the text after the range
  then differs from the recording. The code as written gives the same screen
  as the recording, and the finding says so.
- A prose fix: a sentence in the module doc and in the README. Prose fixes
  nothing in the code.

This round of the review loop is record-only. Each fix is a diff that a review
must read, and that review can find a new nit in it. Then one more fix round
starts.

**The boundary.** This record settles only the form of the parameters that the
restore writes. Each of these occurrences reopens it:

- a restore that writes a color that the recording did not set
- a restore that writes a new color, from the theme or from a rule of the
  filter, in the colon form
- a rewrite inside the range that writes a new color in the colon form
