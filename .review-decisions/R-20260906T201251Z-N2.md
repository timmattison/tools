## `src/wn/src/json.rs` and `src/inscribe/src/main.rs` — two Markdown fence strippers stay two

**Settled** 2026-09-06 (branch issue-462, finding R-20260906T201251Z#N2)

`wn::json::unfenced` and `inscribe::strip_markdown_code_block` both take a
Markdown code fence off a text a model printed. Two functions in one workspace do
one job, and a reader who fixes one finds the other by accident.

The finding is accurate. It is not fixed, because the two functions do not do the
same job, and a shared crate would have to do both.

- **The rules differ, on purpose.** `unfenced` takes the closing fence off only
  when it stands on a line of its own, and it keeps the body of a fence that
  never closed, because a run the deadline killed writes an opening fence and
  stops. `strip_markdown_code_block` takes a trailing three backticks off
  wherever they stand and trims what is left. Neither rule is wrong for its
  caller: `wn` hands the body to `serde_json`, which refuses trailing text, and
  `inscribe` hands the body to a human as a commit message.
- **A shared function would carry a switch.** One crate serving both callers
  either changes the behavior of one of them, or takes an argument that names
  which rule to run. A two-caller interface with a mode flag hides less than
  either function hides today, which is the opposite of what a shared crate is
  for.
- **The subject is thirty lines.** `unfenced` is thirteen lines and
  `strip_markdown_code_block` is seventeen. A workspace crate, its manifest, its
  lint stanza, and its tests cost more than the two of them together.
- **The other repair is prose.** A doc comment in each naming the other changes
  no behavior, and it goes stale the first time either rule moves.

The boundary: this settles the two functions staying separate while they have two
callers with two rules. A third caller, or a change that makes the two rules the
same, reopens it — and so does a defect in either function, which is a finding
about that function and not about the duplication.
