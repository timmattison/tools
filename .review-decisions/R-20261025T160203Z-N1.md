## Commit order on a pushed branch — nine double-press tests of `ha` came after their green commits

**Settled** 2026-10-25 (branch issue-608, finding R-20261025T160203Z#N1)

The review found that nine test commits passed when they were written:
`7ea3e4f6`, `e6cdb796`, `11bf2e84`, `3f4dc022`, `6b6ef948`, `f55e7cf2`, `a5fc9dd6`,
`31fc1af9`, and `c615e02e`. The green commits `354a1f48` and `65c9f58b` already held
their rules: the `take()` of `last_arrow` at the top of `handle_key`, the check that
both presses use the same arrow, the double press on a pull request row, the
inclusive `<=` at 500 ms, and the highlight and non-sticky rules of `expand_all`. The
TDD rule in `CLAUDE.md` asks for the red commit first. The acceptance box of issue
#608 says that each test was red before its fix, and that is not true for decisions
2, 4, 5, and 6. The finding is accurate.

It is not fixed, because the defect is the order of the commits and nothing else.

**The coverage is real.** The body of each of the nine commits names a mutant and
gives the assertion that the mutant fails. The run of `address-issues` for this
finding did three of those mutants again on `1d06c4c1`, with `cargo test -p ha --lib
app::tests` (90 tests pass with no mutant):

- With `gap < DOUBLE_PRESS_WINDOW` in place of `<=` in `press_arrow`,
  `a_second_right_at_exactly_500_ms_is_a_double_press` fails.
- With `let previous = self.last_arrow;` in place of the `take()` in `handle_key`,
  `right_down_right_is_not_a_double_press` and
  `two_fast_lefts_collapse_every_run_and_send_the_empty_set` fail.
- With no `first == arrow` check in `press_arrow`,
  `right_then_left_is_not_a_double_press_of_left`,
  `left_then_right_is_not_a_double_press_of_right`, and
  `two_fast_lefts_collapse_every_run_and_send_the_empty_set` fail.

What TDD gives, a test that can fail for the behavioral reason, is present. Only the
order of the commits is wrong.

**The one fix is a rewrite of pushed history, and it buys nothing durable.** The
finding says that the branch is not pushed. It is: `origin/issue-608` is at
`1d06c4c1`. A red-first order needs the two green commits split, and every later
commit gets a new SHA. The next push then needs a force push, which
`block-dangerous-git.ts` refuses with no override. The review `R-20261025T160203Z`
also ends on `1d06c4c1`, thus after a rewrite `pr-merge-gate.ts` calls the review
`rewritten` and refuses the merge until a fresh review of the whole branch. Against
that: this repository squash-merges every PR with an explicit `--subject` and
`--body`, so no commit of this branch reaches `main`.

**The acceptance box stays unmet as written.** No later commit and no follow-up issue
can make a test red before a fix that already landed. The box holds through the
mutation proof above, not through red commits. The PR that closes issue #608 must say
so, and Tim hears it before the merge.

**The boundary.** This decision settles the order of the nine named commits on the
branch `issue-608` only, where each test exists and a mutant shows that it can fail.
It does not settle a missing test, or a test that nobody showed can fail. It does not
permit a green commit that implements more than its red test asks for, as a habit.
The same defect is now on seven `ha` branches (see the records of
`R-20261017T222526Z-N1`, `R-20261018T041353Z-N1`, `R-20261018T170445Z-N1`,
`R-20261018T235403Z-N1`, `R-20261020T163846Z-N1`, and `R-20261022T182813Z-N1`). A
new occurrence is a reason to look at how the green commits get written, not a
reason to rewrite this branch.
