## `README.md` (the Summarize bullet of `nle`) — the list of the filters that move a rewritten part with its events is closed

**Settled** 2026-11-28 (branch issue-162, finding R-20261128T041228Z#N1)

The finding is accurate in its main claim. The Summarize bullet of the `nle`
entry of `README.md` (lines 6655-6659) says that "a speed change, a
fast-forward, or a redaction" between a screen filter and a summary moves the
rewritten part with its events. Typing speed, pause removal, pause insertion,
and auto-trim also keep the type and the data of each event in its order
(`src/nle/src/filters.rs` and `src/nle/src/filters/typing_speed.rs`), thus they
also move the part. Neither sentence of the bullet names them.

**The proposed fix is wrong at HEAD.** The finding states the rule as the count
of events. 65b04991 changed the rule after this review. A step now moves a part
with its events only when it answers as many events as its region held, and
each answered event has the type of the region event at its index and keeps its
data or its time (`RewrittenParts::move_through`, `src/nle/src/pipeline.rs`). A
step that keeps the count and answers its events in a different order does not
pair. Thus the text "keeps the count of events" is false, and a later fix must
not use it.

No output is wrong. The three named filters do move the part, and a summary
that the README does not describe gives a failure that names its reason.

**The fix costs more than the defect.** The fix is prose in one bullet. This
round of the review loop is record-only. A changed bullet is new text that a
review must read, and that review can start one more fix round.

**The boundary.** This record settles only the closed list of the filters that
move a rewritten part. These occurrences reopen it:

- a README statement that a filter moves the part when the code does not pair
  it, or that a filter does not move the part when the code pairs it
- a README statement of the pairing rule that differs from
  `RewrittenParts::move_through`
