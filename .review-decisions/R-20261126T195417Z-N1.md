## `src/nle/src/filters.rs` — `trim_silence` clamps the events in the order of its input, and does not sort them first

**Settled** 2026-11-26 (branch issue-154, finding R-20261126T195417Z#N1)

The finding is accurate. `FilterRegistry::run` gives the first filter its
events in the order of its input. When that order is not time order, the
leading clamp of `trim_silence` gives two output events the time 0 in the
order of the vector. The stable sort of step 7 keeps that order. Thus
`builtin().run(vec![output(3.0), output(2.0), input(5.0)], …)` plays the
output of 3 s before the output of 2 s. The trailing clamp has the same rule.
`remove_pauses` sorts first, and `trim_silence` does not.

The app does not reach this defect. The app renders only through
`FilterRegistry::render`, and `render` sorts the events with a stable sort
(`src/nle/src/pipeline.rs:361`) before the first filter. Each later filter
gets the result of step 7, which is in time order. Only the tests call
`FilterRegistry::run`, and no test gives `trim_silence` events out of time
order.

The cost of a fix: one sort and one test, which is new code that a review
must read. That review can find a new nit, and the review loop starts one more
round for a defect that no user can see.

**The boundary.** This decision settles the order of the clamped events of
`trim_silence` for input that is not in time order, while `render` sorts its
events and only tests call `run`. These events reopen it:

- a caller of `FilterRegistry::run` outside the tests,
- a change that removes the sort of `render`, or
- a change to the pipeline that gives a filter its events out of time order.
