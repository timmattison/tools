## `src/nle/src/filters/keystroke_hud/keys.rs` — a pending CSI start is parsed again from its `ESC` for each event that joins it

**Settled** 2026-11-27 (branch issue-161, finding R-20261127T213649Z#N1)

The finding is correct. 195ea40d made the cost linear only for a pending
string (`scan_from`, `skip_string`). A CSI start that waits for its final byte
calls `defer(start, 0)` in `escape` and in `csi`. `feed` then appends each
input event that comes within `SEQUENCE_TIMEOUT` (50 ms) to the pending
characters and parses again from index 0. Thus `csi` reads all of the earlier
parameter characters again for each event that joins, and the cost is in the
square of the count of those events.

The case needs `ESC [` and then parameter characters only, in many input
events with gaps of 50 ms or less. A terminal sends a CSI key of fewer than 20
characters, in one read. Only a malformed recording gives the case, and the
HUD then loses no key and gives no wrong key: the cost is time. The fix is a
limit on the length of a pending CSI, which is a new rule in the state machine
of `feed`. That rule is new code that a review must read, and that review can
start a new fix round. This round of the review loop is record-only.

Boundary: a change to the join rule of `feed`, or to the `defer` calls of a
CSI start, reopens this decision. A real recording where the HUD render is slow
because of a pending CSI reopens it too. A new argument about a limit does not.
The decision R-20261127T132506Z-N4 covers the delay of the key times of a
pending string, and this decision does not change it.
