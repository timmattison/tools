## `src/nle/src/filters/keystroke_hud/keys.rs` — `ss3` reads no modifier digit, so `ESC O 2 P` shows as `P`

**Settled** 2026-11-27 (branch issue-161, finding R-20261127T221643Z#N1)

The finding is correct. `ss3` reads one character after `ESC O` and gives it
to `ss3_key`. Some terminals, for example Konsole and older xterm, send
`ESC O 2 P` for Shift+F1. `ss3_key('2')` gives `None`, the reader drops the
`2`, and the `P` then parses as typed text. Thus the HUD shows `P`, a key that
the user did not press. An unknown final character after `ESC O`, for example
`ESC O z`, is dropped too. No case of `ss3_keys` holds a digit after `ESC O`.

The defect is a wrong label for one legacy encoding of the modified keys F1 to
F4. The xterm form `CSI 1;2 P` goes through `csi_letter_label` and the modifier
field, as the cursor keys do, so a terminal that sends the CSI form gives the
correct label. The HUD loses no other key, and the box of the next key is
correct.

The fix is a new branch in the state machine of `ss3`: a run of digits as a
modifier value, given to `Mods::from_value`, and new cases in `ss3_keys`. That
branch is new code that a review must read, and that review can start a new
fix round. This round of the review loop is record-only.

Boundary: a change to `ss3` or to `ss3_key` reopens this decision. A recording
from a terminal that sends `ESC O <digit> <final>`, where the HUD shows the
wrong key, reopens it too. A new argument about the encoding does not. The
decision R-20261127T132506Z-N3 covers `ESC ESC [ D`, and this decision does not
change it.
