## `src/nle/src/commands.rs` — the end of a link chain needs only the picked ending, not the longest one

**Settled** 2026-11-26 (branch issue-158, finding R-20261126T205525Z#N1)

The finding is accurate. `matching_ending` picks the longest of `endings`
that the path ends with. But `resolve_output_path` then accepts an end of
the chain whose name ends with that ending. It does not ask which ending is
the longest for the name of the end of the chain. For a set where one ending
is a suffix of another, for example `[".gz", ".json.gz"]`, a link `a.gz` to
`b.json.gz` thus passes.

No current input shows the gap:

- `RECORDING_ENDINGS` is `[".json", ".json.gz"]`. `.json` is not a suffix of
  `.json.gz`, so no name ends with both.
- `VIDEO_ENDINGS` is `[".mp4", ".gif"]`, and `WEB_ENDINGS` is `[".html"]`.
  Neither set holds a suffix pair.
- `GZIP_ENDINGS` goes only to `has_ending`, never to `resolve_output_path`.

The cost of a fix: a change to the check of the end of the chain, a new unit
test with an invented set of endings, and a correction of the doc of
`resolve_output_path`. That fix is new code, and it starts one more review
round, which can find a new nit in the new code. The defect has no effect
until a caller passes a set with a suffix pair.

The boundary: a report that the two checks apply different rules to a set
that no caller passes is this decision. These changes reopen it:

- A constant or a caller passes to `resolve_output_path` a set where one
  ending is a suffix of another.
- A link with a current set of endings reaches a file of another format.
