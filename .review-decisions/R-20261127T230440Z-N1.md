## `src/nle/src/filters/keystroke_hud/keys.rs` — `parse_final` drops the `paste_tail` of its parse

**Settled** 2026-11-27 (branch issue-161, finding R-20261127T230440Z#N1)

The finding is correct. `parse_final` keeps only the keys of its parse. A
pending string start (`ESC ]`, `ESC P` or `ESC _`) with no terminator whose
rest holds `ESC [ 200 ~` opens a paste in that final parse. `feed` then parses
the next input event with the `paste_tail` from before, which is empty. Thus
`feed(1.0, "\x1b]x\x1b[200~abc")` and then `feed(2.0, "def\x1b[201~")` give
`Alt+]`, `x`, `Paste`, and then `def` as typed text. The README says that a
bracketed paste shows none of the pasted text.

The case needs `Alt+]`, and then the start of a bracketed paste in the same
input event or within `SEQUENCE_TIMEOUT` (50 ms). The rest of the paste must
then come more than 50 ms after that. A person cannot give that order of input
in normal use, and the HUD then shows the end of one paste as typed text. It
shows no text that is not on the screen: zsh and bash turn on the mode only at
the prompt, where the line editor shows the pasted text. `finish` clears
`paste_tail` on purpose, because no input comes after it.

The fix changes the state machine of `feed`: `parse_final` must give its
`paste_tail`, and `feed` must scan the new data for the end of the paste
before the normal parse. That change is new code and a new test that a review
must read, and that review can start a new fix round. This round of the
review loop is record-only.

Boundary: a change to `parse_final`, or to how `feed` sets `paste_tail`,
reopens this decision. A recording where the HUD shows pasted text after a
paste start that is not inside a pending string reopens it too. A new argument
about the timing does not. The decision R-20261127T132506Z-N4 covers the span
of a pending string start, and this decision does not change it.
