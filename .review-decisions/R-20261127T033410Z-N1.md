## `specs/2026-11-26-nle-plugin-architecture-design.md` the cache of compiled code — the host trusts each cache file as native code, and the spec does not say so

**Settled** 2026-11-26 (branch issue-169, finding R-20261127T033410Z#N1)

The finding is accurate. "The host" gives a reason why the host does not call
`Component::deserialize`: that function is `unsafe`, because it trusts the
bytes that it reads. The same bullet turns on the compilation cache of
wasmtime. The finding reads wasmtime 48, which loads the bytes of a cache file
on a hit through `engine.load_code_bytes`. That is the same path as
`deserialize`, and it does not make sure that the bytes are valid code. Thus
the host trusts each file under `dirs::cache_dir()` as native code, and the
spec does not say so.

This trust is not a way out of the sandbox. A plugin cannot write to the
cache, because its world imports no file interface and its WASI context has no
preopened directory. `dirs::cache_dir()` is a directory of one user:
`~/Library/Caches` on macOS, and `$XDG_CACHE_HOME` or `~/.cache` on Linux. Only
a process of that user can write there. Such a process can also replace the
binary of the editor, thus the cache gives it no new power.

**The fix costs more than the defect in this round.** The fix is prose: one
sentence in the bullet, and one row in the security table. It changes no
behavior of the host. This round of the review loop is record-only. A change of
the spec starts one more review cycle, and that review can find a new nit in
the new text.

**The boundary.** This record settles only the trust of a cache directory that
only its user can write. Each of these occurrences reopens this record:

- the cache directory is shared between users, or a different user can write
  to it
- a plugin gets a way to write a file
- the host loads compiled code from a different place, or calls
  `Component::deserialize`
