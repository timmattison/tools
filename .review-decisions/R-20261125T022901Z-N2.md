## `src/msgs/frontend/src/messages.ts` — `openConversationAt` shows the missing-hit notice for each failure of `get_message_position`

**Settled** 2026-11-25 (branch msgs, finding R-20261125T022901Z#N2)

The finding is accurate. The `catch` of `openConversationAt` shows
`MISSING_HIT_NOTICE` ("The message of this search result is no longer in this
chat.") for each rejection of `get_message_position`. A rejection can also come
from a database that is not open, a poisoned lock, or a failed SQLite query.
The test rejects only with `Message 5 is not in chat 1`.

**The fix costs more than the defect.** The other failures are rare, because
msgs reads a local database that it opened before the search. After the
notice, the chat opens at its newest message through `loadPage`. If the
database failed, `loadPage` fails too, and its `catch` shows the real text of
the error with `showNotice(messageOf(e))`. Thus the user sees the real cause
below the wrong notice. A fix needs a check of the error text or a new error
kind from the backend, and a test of each. This round of the review loop is
record-only, thus that change starts one more review cycle.

**The boundary.** This record settles the text of the notice on a failure of
`get_message_position` only. A failure that shows the missing-hit notice and no
real cause, or a missing message that shows a different notice, reopens this
record.
