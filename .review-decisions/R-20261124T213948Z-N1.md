## `src/drun/src/docker_args.rs` — a one-letter value flag with only `=` after it takes the next argument

**Settled** 2026-11-24 (branch drun, finding R-20261124T213948Z#N1)

The finding is accurate. `scan_short_group` removes a leading `=` from the
text after a one-letter flag that takes a value. When nothing follows the `=`,
it reads the next argument as the value. pflag gives such a flag the value `=`
and reads no argument. Thus `drun run -e= -d alpine` reads `-d` as the value
of `-e`, and `drun run -h= alpine` finds no image and gives exit status 2.

**The fix costs more than the defect, because docker refuses this input.**
With docker 29.9.2, the docker client refuses the value `=` for `-e`, `-l`,
`-m`, `-c`, and `-a` before it asks a daemon ("invalid environment variable:
=", "invalid label '=': empty name", "invalid size: '='"). For `-w`, `-p`,
`-v`, and `-u`, the value `=` is not a working directory, a port, a volume, or
a user that a container can start with. `drun run` adds its label and a name,
and then gives the arguments of the user to docker with no change. Thus docker
gives its own refusal in each of these cases. Only
`-h=`, a host name of `=`, can start a container, and no person writes that
host name. The parser is in the code that each round of this branch changed,
and each change of it started a new review round.

The boundary: a non-blocking finding that the parser of `drun` reads a value
that docker refuses in a different way from pflag is a re-litigation of this
decision. A finding where `drun` starts a container on a different host, or
with different arguments, from the arguments that the user gave is not
covered.
