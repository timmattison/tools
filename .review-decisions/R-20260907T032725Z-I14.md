## `vouchers delete <id>` — an explicitly named UUID is its own confirmation

**Settled** 2026-09-07 (branch ufa, finding R-20260907T032725Z#I14)

`delete_voucher` sends the `DELETE` as soon as it is called. Its bulk sibling
`delete_vouchers_filtered` lists the matches, asks, and refuses a non-terminal
run without `--yes`. The review read that asymmetry as an oversight, and it
asked for one of two answers: route the single deletion through
`confirm_destructive` too, or record why it needs no confirmation.

The finding is accurate about the asymmetry. The single deletion is not
changed, and this record is the reasoning the review asked for. The missing
test *was* a real gap and it is fixed: `deleting_one_voucher_sends_a_delete_for_the_id_it_was_given`
reads the request the controller got and fails when the path names another
voucher.

**A confirmation answers a question the user has already answered.** The two
commands differ in what the user knows at the moment they press return.
`ufa vouchers delete-filtered --filter "expired eq true"` names a *rule*, and
the controller decides what the rule selects. The user cannot know the count
or the contents until the controller answers, which is why that command lists
the matches first and then asks about the list. `ufa vouchers delete
<uuid>` names one row, by the identifier the controller itself printed. There
is no set to reveal and no count to be surprised by: the question
`Delete 1 voucher(s)?` restates the command back to the person who typed it.

**A prompt that always says the same thing trains the user to answer without
reading.** That cost lands on the prompts that carry information, which are the
bulk ones. A confirmation is worth its keystroke when it can surprise the
reader.

**The blast radius is one voucher, and a voucher is cheap.** A voucher is a
guest access code. `ufa vouchers create` makes another one in a single command.

**The boundary.** This settles a destructive command whose entire effect is
named by an identifier the user typed, where the effect is one object and the
count is knowable before the command runs. It does not settle:

- **A destructive command that takes a rule, a glob, a filter or an empty
  argument list.** Those decide their own scope, and they confirm. That is the
  design `delete_vouchers_filtered` already holds.
- **A destructive command whose one named object carries others with it** — a
  site, a network, a device with clients behind it. The identifier names one
  row and the deletion reaches further than the row, so the user cannot know
  the effect from the command they typed.
- **An irreversible command.** A voucher is re-creatable in one step. A
  deletion that destroys collected data is a different trade and gets its own
  answer.
- **The missing test.** A finding that a destructive path has no test is real
  whatever this record says. This decision covers the confirmation, and only
  the confirmation.
