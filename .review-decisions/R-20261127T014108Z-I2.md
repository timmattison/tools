## `src/nle/src/filters/idle_compression.rs` — the cost of the cell compare is O(output events × cells), and it stays

**Settled** 2026-11-27 (branch issue-167, finding R-20261127T014108Z#I2)

The finding is accurate. After each output event, `activity_times` compares
each cell of the watched rows with the copy in `shown`. Thus a render costs
(output events) × (watched cells). `MAX_SCREEN_CELLS` lets a header of
65535 × 64 cells through, and a crafted recording with that header and 100,000
output events asks for about 4e11 cell compares. The render runs in the window.
A `Cell` is 16 bytes, so the grid of the emulator and `shown` hold about 67 MB
each.

The fix costs more than the defect, for three reasons:

- **The emulator costs the same order, and the filter cannot change that.**
  `scroll_up` (`src/termstate/src/lib.rs:728`) copies each cell of the scroll
  region, and `clear_screen` (`:760`) writes each cell of the screen. A crafted
  file with the same header and 100,000 newlines on the bottom row costs about
  4e11 cell writes in `process_output` alone. The compare of the filter
  doubles that worst case. It does not make it.
- **The exact fix changes a shared crate, and a defect in it gives a wrong
  result.** To compare only the cells that an event wrote, `termstate` must
  record each write. Its grid has about 20 write sites, and `beta` uses the
  same crate. A missed site makes the filter compress a period in which the
  screen changed. A wrong render is worse than a slow one, and this fix still
  leaves the first reason.
- **A lower cap or a work budget refuses real recordings.** A budget of
  events × cells that stops the crafted file at once also refuses a long
  recording from a large real terminal (300 × 80 cells and 200,000 output
  events). A lower `MAX_SCREEN_CELLS` keeps the cost at events × cap.

**What the accepted consequence is.** A recording from outside with a header
that no real terminal gives can make the render of an idle compression slow,
and the window waits for it. No data on disk changes. The render of a real
recording costs about 1 ns for each cell compare: 10,000 cells and 100,000
output events take about 1 s. The fix that removes the wait is a render off
the thread of the window, which is a change to the editor and the window, and
not to this filter.

**The boundary.** This decision settles the cost of the per-event compare of
the watched rows, and the memory of the grid and its one copy. A new argument
about the same cost does not reopen it. These reopen it:

- a change that makes the filter cost more than O(watched cells) for one
  output event, or keep more than one copy of the grid;
- a second filter or a second path that adds its own O(cells) pass for each
  event;
- a change to `termstate` that records the cells that each write changes,
  because then the exact fix costs little.
