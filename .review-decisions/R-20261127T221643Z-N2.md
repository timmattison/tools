## `src/nle/src/filters/keystroke_hud/keys.rs` — a CSI code that overflows `u32` takes the default code 1

**Settled** 2026-11-27 (branch issue-161, finding R-20261127T221643Z#N2)

The finding is correct. `CsiParams` keeps a number that does not fit in `u32`
as absent, and `code` then gives the default 1. Thus
`CSI 99999999999999999999 ~` shows `Home`, a key that the user did not press.
The test `incomplete_and_oversized_sequences_do_not_panic` expects `Home` for
that input, and its comment states the rule, so the test holds the label in
place. There is no panic.

No terminal sends a key code of 20 digits. The tilde codes have 3 digits or
fewer, for example `200` of a paste start. Only a malformed recording gives
the case, and the HUD
then shows one wrong box for bytes that are not a key. The test exists to
prove that such bytes do not cause a panic, and that proof holds.

The fix changes the meaning of an absent number in `CsiParams`: an overflow
must stay apart from an empty field, and `csi_tilde_label` must then give no
key. That change is new code and a changed test that a review must read, and
that review can start a new fix round. This round of the review loop is
record-only.

Boundary: a change to how `CsiParams` keeps an overflowing number, or to the
default of `code`, reopens this decision. A key code that a real terminal
sends and that overflows `u32` reopens it too. A new argument about malformed
input does not.
