## `src/drun/src/main.rs` `rm` — a spawn error of docker for one host stops the loop of the hosts

**Settled** 2026-11-25 (branch drun, finding R-20261125T234924Z#N1)

The finding is accurate. The doc comment of `rm` says that it tries every host,
and that it exits with the first exit status that is not zero. The call
`.status().map_err(cannot_start)?` leaves the loop on a spawn error. Thus `rm`
does not try the hosts after that host. It exits 125 (`EXIT_NOT_STARTED`), also
when an earlier host already failed with a different status.

**The risk is low.** A spawn error is rare here. `fleet::inventory` started the
same docker for every host just before the loop, thus the binary exists and
starts. Only a transient failure of the operating system, for example a fork
that fails with `EAGAIN`, can cause it. `rm` removes no wrong container: the
plan holds only the containers that `locate` found on each host. The exit
status is not zero, and the message names the cause, thus the person sees the
failure and runs `drun rm` again.

**The cost of the fix is a new review cycle.** This round of the review loop is
record-only. The fix keeps `Failure::NotStarted` as the first failure, continues
with the next host, and returns the first failure after the loop. That change
needs a red test with a fake docker that fails to start for one host only. It is
new code in `main.rs` and in the tests, which a fresh review must read, and a
fresh review can find a new nit in it. Then a new fix round starts, and the loop
does not end clean.

**The boundary.** This decision settles only a failure to start docker for one
host of the plan. A defect in which `rm` removes a container on the wrong host,
or removes a container when `locate` cannot find another one, is a new finding.
A defect in which `rm` exits 0 after a failure is a new finding too.
