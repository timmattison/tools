## Commit order on an unpushed branch — the job counts of the `ha` Running header came before their tests

**Settled** 2026-11-02 (branch issue-627, finding R-20261102T134608Z#N1)

The review found that the green commit `3f107b33` added three behaviors that
its red commit `1fe2bb8d` does not test:

- A run whose fetch failed adds its last good jobs to the counts.
- A job in the state Cancelled or Other is in no count.
- A finished run adds nothing to the counts.

The tests of these behaviors came after the green commit. They are
`a_run_with_no_answer_adds_nothing_and_a_failed_fetch_adds_its_last_good_jobs`
in `eb1b3478`, `a_cancelled_job_and_a_job_in_the_state_other_are_in_no_count`
in `d759f3a5`, and `the_jobs_of_a_finished_run_are_in_no_count` in `2a684fcf`.
They passed when they were written. The TDD rule in `CLAUDE.md` asks for the
red commit first. The finding is accurate.

It is not fixed, because the defect is the order of the commits and nothing
else.

**The coverage is real.** Three mutants ran on `390208e1`, one at a time, with
`cargo test -p ha --lib board::tests` (138 tests, all pass on unmutated HEAD).
The file was restored after each mutant, and `git status --short` was empty at
the end.

- M1: the arm `Jobs::Failed { jobs, .. }` removed from `active_jobs`, thus the
  match reads `Some(Jobs::Ready(jobs)) => jobs.as_slice()`.
  `a_run_with_no_answer_adds_nothing_and_a_failed_fetch_adds_its_last_good_jobs`
  fails (137 pass, 1 fail).
- M2: `RunState::Cancelled` in `JobCounts::add` changed to add to
  `self.failed`, with `RunState::Other => {}` kept.
  `a_cancelled_job_and_a_job_in_the_state_other_are_in_no_count` fails (137
  pass, 1 fail).
- M3: the call `self.active_job_counts(&active)` changed to take the active
  runs chained with the recent runs.
  `the_jobs_of_a_finished_run_are_in_no_count` fails (137 pass, 1 fail).

Each test can fail for the behavioral reason. Only the order of the commits is
wrong.

**A reorder does not make a red, and the real fix buys nothing durable.** The
branch is not pushed, thus a rewrite needs no force push. But the counts do not
exist before `3f107b33`. A move of the tests to before that commit gives a
compile error, not a behavioral red. A real red needs a split of `3f107b33`.
The tool is an interactive rebase, which only Tim can run. Every later commit
then gets a new SHA. The review `R-20261102T134608Z` ends on `390208e1`, thus
after a rewrite `pr-merge-gate.ts` calls the review `rewritten` and refuses the
merge until a fresh review of the whole branch. Against that: this repository
squash-merges each PR with an explicit `--subject` and `--body`, thus no commit
of this branch reaches `main`.

**The boundary.** This decision settles the order of the named commits on the
branch `issue-627` only, where each test exists and a mutant shows that it can
fail. It does not settle a missing test, or a test that nobody showed can fail.
It does not permit a green commit that implements more than its red test asks
for, as a habit.

**The pattern.** This is the eleventh branch with this shape. The record
`R-20261101T170934Z-N1` lists the earlier ten. The repair belongs to issue #22
of timmattison/dotfiles, and not to this record.
