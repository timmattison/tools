## `src/ufa/src/site_manager/client.rs` — `get_hosts` has no bound on the count of pages

**Settled** 2026-11-25 (branch ufa, finding R-20261125T155649Z#N1)

The finding is accurate. The controller walk (`collect_pages` in
`src/ufa/src/pagination.rs`) refuses a server that states more than
`MAX_COLLECTION_ITEMS`. The cloud walk, `get_hosts`, has one guard only: it
refuses a `nextToken` that it sent before. A server that gives a new token on
each page makes `ufa cloud hosts` send requests with no end, and `hosts` and
`sent_tokens` grow with no limit. The doc of `get_hosts` states this gap.

**The cost is a new review cycle.** This round of the review loop is
record-only. A cap on the pages is new code, a new error, and a new test, and a
fresh review can find a new nit in each. Then a new fix round starts, and the
loop does not end clean. The risk is low. `SiteManagerClient::new` names
`https://api.ui.com/v1/` and no other host, and it never waives the
certificate check. Thus only Ubiquiti, or a party that holds a valid
certificate for `api.ui.com`, can give the endless tokens. The controller walk
got its bound because a controller is a host on the LAN, often behind
`--insecure`. Each page of the cloud walk is still bounded:
`read_json_response` caps each answer at `MAX_RESPONSE_BYTES`, and the
request timeouts of `build_client` apply to each request.

**The boundary.** This decision settles only the count of pages of
`get_hosts` against the fixed `api.ui.com` host. A change that lets a user or
a configuration point the Site Manager client at a different host, or that
waives its certificate check, reopens it. A different page walk with no bound
is a new finding. R-20261125T160218Z#N3 reports the same gap, and its record
points to this one.
