## `src/ufa/src/main.rs` — a 403 still makes `ufa` read the key from 1Password again

**Settled** 2026-11-26 (branch ufa, finding R-20261126T031142Z#N2)

The review found that `run_with_the_current_key` reads the key from 1Password
again after a 401 and after a 403. The setup wizard reads a 403 as a key that
the controller took, with limited permissions. For such a key, each command
that gets a 403 forgets the op-cache copy, runs `op` again, and returns the
first error. No result is wrong, but each such command pays one more read of
1Password.

The finding is accurate. The fix that it gives, a read again after a 401
only, is declined.

**Why the 403 stays.** The read again exists for one case: the user rotated
the key in 1Password, and op-cache still holds the old key. No test on a real
controller or on the Site Manager API shows that a revoked key always gets a
401 and never a 403. If a revoked key gets a 403 and the rule reads only after
a 401, each command fails until the user finds the cache file and deletes it.
The README no longer tells the user to do that. A key with limited permissions
pays one read of 1Password for each refused command. That cost is smaller, and
the user can see it.

Commit `ae90f5828` states the cost in the doc of `run_with_the_current_key` and
in the README.

**The boundary.** This decision settles the choice of 401 or 403 as the
statuses that start the read again. It does not settle a read again that
changes a result, a second run of a command that is not safe, or a read again
for a key that came from no 1Password reference. If a check on a real
controller shows that a revoked key always gets a 401, the narrower rule is a
new finding.
