## `src/nle/src/filters/splice.rs` — no test puts a multi-byte character before a sequence that is open at the end of a region

**Settled** 2026-11-28 (branch issue-166, finding R-20261128T033220Z#N1)

The finding is accurate. `Splicer::finish` puts the tail into the event with
`insert_str(offset, ..)`, at the offset that `mark` recorded. The one test of
that path, `finish_puts_the_tail_before_a_sequence_that_is_open` in
`src/nle/src/filters/splice/tests.rs`, feeds only ASCII text ("ab\x1b[1") before
the open sequence. The `CLAUDE.md` rule "UTF-8 String Safety" asks for a test
with multi-byte characters.

No output is wrong. `mark` and `push` record `data.len()`, which is a byte
offset. Each recorded offset is the length of the data before a `push` of a
whole `char`, thus each offset is on a character boundary, and `insert_str`
does not panic. The truncate path of `Splicer::complete` uses the same offsets,
and `src/nle/src/filters/cursor/tests.rs` holds a multi-byte case of that path.
The gap is a test that holds the present offsets against a future change of
`mark` or `push` from bytes to characters.

**The fix costs more than the defect.** This round of the review loop is
record-only. A new test is new code that a fresh review must read, and that
review can start one more fix round. The offsets come from one place, and the
existing multi-byte test of the truncate path fails for the same change of
`mark` or `push`.

**The boundary.** This record settles only the missing multi-byte test of the
`finish` path. These occurrences reopen it:

- a change of `mark`, `push`, or `finish` that computes an offset from a count
  of characters, or from a source other than `data.len()`
- a removal or a change of the multi-byte test of the truncate path
- a new path of the splicer that inserts text at a recorded offset
