## `src/glance/src/shell.rs` — `draw_charts` makes the glyphs of the label again at each tick, with no cache

**Settled** 2026-11-16 (branch issue-696, finding R-20261116T105513Z#N3)

The finding is accurate. At each tick, `draw_charts` calls `draw_label` for
each scale, and `label_glyphs` makes two transparent bitmaps and draws the host
name two times, once in each ink. The glyphs depend only on the host name and
the `Geometry`, thus a steady tick computes the same coverage again. The path
before commit 30e127e2 drew the text one time for each scale.

**The cost of the defect.** A temporary test timed the path in a release build
on 2026-11-16, at a load average of 13. After a warm-up, `label_glyphs` took
0.06 ms to 0.1 ms for each scale, and `render` with `draw_label` took 0.12 ms to
0.2 ms. At the default interval of 1 second and two scales, that is less than
0.04% of one core. The status item, the bitmap representations, and
`setImage` cost AppKit time at each tick in any case, and a cache does not
remove them.

**The cost of the fix.** A cache needs state in the `Ivars` of `Monitor`, a key
of the host name and the `Geometry` for each scale, and a rule that removes the
entries of a scale that no screen has now. Each of these needs a test, and each
is one more place where a change of the host name, of the thickness of the
status bar, of the scale of a screen, or of the line height of the font can
show a stale label. Tim chose to decline the finding in the run that settled
it.

**The boundary.** This decision ends when a measurement shows the label above
1 ms for each tick, when the default interval goes below 1 second, or when a
profile of glance shows `label_glyphs` as a large part of its CPU time. A new
argument that the work is repeated, with no new measurement, does not reopen
it.
