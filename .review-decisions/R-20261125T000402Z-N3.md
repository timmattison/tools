## `src/nle` — the open recording stays in the webview until issue #149

**Settled** 2026-11-25 (branch 170, finding R-20261125T000402Z#N3)

The finding is accurate. After `load_recording` returns, the Rust side keeps
no copy of the recording, because there is no `tauri::State`.
`src/nle/frontend/src/App.tsx` keeps the `LoadedRecording` in `useState`, and
`save_recording(path, recording, compress)` in `src/nle/src/commands.rs` takes
the full `Recording` from the webview. `~/.claude/TAURI.md` asks for the Rust
backend as the single source of truth.

Tim decided:

- **This branch stays the scaffold that issue #170 gives.** Issue #170 itself
  gives `save_recording(path, recording)`, and the frontend only shows a
  snapshot of the metadata today. Commit c2c95f68 changes `README.md` from
  "The Rust side owns every recording" to "The Rust side reads and writes
  every recording file", which is true today.
- **Issue #149 moves the open recording into Rust state.** The editing engine
  of issue #149 must keep the open recording in Rust state, and
  `save_recording` must then take only a path (and its `compress` option).
  A comment on issue #149 records this decision:
  <https://github.com/timmattison/tools/issues/149#issuecomment-7150387706>.

The boundary: on this branch (issue #170, PR #172, branch 170), a report that
Rust keeps no state for the open recording, or that `save_recording` takes a
`Recording` from the webview, is this decision. A text that says that the Rust
side owns or keeps the recording reopens it, because that text is false until
issue #149 is done.
