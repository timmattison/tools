## `src/workit/src/main.rs` — the worktree filter counts a manifest before it reads it

**Settled** 2026-11-25 (branch workit, finding R-20261125T043207Z#N1)

The finding is accurate. `find_cargo_tomls` counts each `Cargo.toml` in a
worktree below the search path before `is_package_toml` reads it. Thus
`Scan::worktrees` also counts a workspace manifest and a manifest that does not
parse. If the filter took out only such manifests, `explain_empty_result` names
`--include-worktrees`, and that flag lists no package.

The defect is small:

- **The case is narrow.** Each manifest that the filter took out is in a
  worktree, and none of them is a package. A worktree is a second checkout of
  the same repository. Thus a worktree that holds a workspace manifest almost
  always holds the packages of that workspace too. Then the count is too high,
  but the advice is correct.
- **No manifest is wrong.** An empty result prints its message, writes
  nothing, and exits 0. A run with `--include-worktrees` then also writes
  nothing. The cost to the user is one run with a flag.

**The cost is a new review cycle.** This round of the review loop is
record-only. A fix moves the read of each manifest in a worktree before the
count, changes the doc of `Scan`, and adds a test. A review must read that new
code, and a fresh review can find a new nit in it. At the stall (decision
H-742-2 on issue #742), Tim chose to fix each blocking finding and to settle
each nit with a record.

**The boundary.** This decision settles the count of `Scan::worktrees` and the
message of `explain_empty_result` for a manifest in a worktree that is not a
package. A count that changes which packages a run lists or writes is a new
finding. A message that names a flag in a different case is a new finding.
