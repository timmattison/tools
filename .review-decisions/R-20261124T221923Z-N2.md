## `src/msgs/src/cache.rs` — a second `msgs` process during the first build gets a lock error

**Settled** 2026-11-24 (branch msgs, finding R-20261124T221923Z#N2)

The finding is accurate. `TextCache::open_at` writes `PRAGMA user_version` at
each open, and the rebuild holds one write transaction for the whole build. A
second `msgs` process that starts during the build of the first waits for the
busy timeout of rusqlite (5 s by default). Then it stores
`Failed("database is locked")`, and its search does not operate for that run.
No test starts two processes.

**The fix costs more than the defect.** A fix needs a single-instance plugin,
or a change of the open sequence and of the busy timeout. It also needs a test
with two cache handles on one file during a rebuild. The defect needs two
windows of the same app at the same time, during the first build after a change
of `chat.db`. The first process continues to operate. The second process shows
a search error, not a wrong result, and a start of it after the build gives a
working search. This round of the review loop is record-only, thus the fix also
starts one more review cycle.

**The boundary.** This record settles the case of two `msgs` processes on one
cache file only. A lock failure with one process reopens this record. A wrong
search result in either process also reopens it.

**Superseded** 2026-11-24 (finding R-20261124T203119Z#I17). The index has no file. Thus two processes share no cache file, and the lock case is gone.
