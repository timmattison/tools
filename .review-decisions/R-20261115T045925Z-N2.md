## `src/chf/src/index.rs` `process_folder` — `CacheEntry` is copied field by field

**Settled** 2026-11-19 (branch issue-674, finding R-20261115T045925Z#N2)

The finding is accurate. `CacheEntry` does not derive `Clone`, so `process_folder` builds a copy field by field at two sites: the branch for a transcript that chf can not stat, and the branch for a cache hit. The first copy also makes rustfmt indent the whole `let stat = match` block one level deeper. `Session` derives `Clone` (`src/chf/src/session.rs:39`). Thus `#[derive(Clone)]` on `CacheEntry` and `..entry.clone()` can replace both copies.

**Why it is not fixed.** The defect is in the style only, not in the behavior:

- Both copies are struct literals that name all four fields with no `..` base. A new field of `CacheEntry` thus fails the build at both sites until each site names it. No copy can drop a field silently.
- The review loop of this branch is in its record-only round. A code change goes into the next incremental review, and the sweep of nits starts again.

**The boundary.** This record settles the two field-by-field copies of `CacheEntry` in `process_folder` on branch `issue-674`. It does not permit a hand-written clone that can drop or change a field silently, for example one that uses a `..Default::default()` base.
