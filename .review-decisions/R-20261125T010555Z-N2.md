## `src/ic/src/main.rs` — `ic` ignores a value of `IC_PROTOCOL` that it does not know, with no message

**Settled** 2026-11-24 (branch ic-xtermjs, finding R-20261125T010555Z#N2)

The finding is accurate. `forced_protocol` gives the value of `IC_PROTOCOL` to
the parser of clap, and it drops a value that the parser refuses. Thus a user
who exports `IC_PROTOCOL=iterm` or `IC_PROTOCOL=sixle` gets the protocol that
`termgfx` selects, and gets no message about the variable. The flag refuses
the same typo through clap.

The silent ignore is a choice of design, and the finding says so. The README
section "Forcing a Protocol" states it: "`ic` ignores a value of `IC_PROTOCOL`
that it does not know, and selects the protocol as it does for `auto`." The
test `forced_env_unrecognised_is_no_override` holds it. The variable is a
setting for a whole shell session, and a session setting that is not correct
gives the same result as no setting.

**The cost is a new review cycle and a new behavior.** This round of the review
loop is record-only. A warning is a new line on stderr in each path that reads
the variable: a file, stdin, a video, monitor mode, and `--will-display`. Each
path needs a test of the text and of the condition. That is new code that a
review must read, and a fresh review can find a new nit in it. Then a new fix
round starts, and the loop does not end clean.

**The boundary.** This decision settles only the silent ignore of a value that
`ic` does not know. A value that `ic` knows and reads wrong, for example
`SIXEL` that does not force Sixel, is a new finding. A document that states
that `ic` refuses or warns about an unknown value is a new finding.
