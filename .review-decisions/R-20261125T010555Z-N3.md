## `src/ic/src/main.rs` — `--will-display` with a forced protocol reads the remote transport that no verdict reads

**Settled** 2026-11-24 (branch ic-xtermjs, finding R-20261125T010555Z#N3)

The finding is accurate. With a forced protocol, `report_display_readiness`
calls `detect_remote_transport` before the gate. The gate then gives `Ok` on
`TerminalType::Forced` before it reads the transport. Thus the call starts
`ps -eo pid=,ppid=,comm=`, and under Zellij a second `ps -eo pid=,args=`, for
an answer that no verdict reads. The display path reads the transport for
`payload_budget_for`, so only `--will-display` has the extra cost.

The verdict is correct. The cost of the defect is the run time of one or two
`ps` processes on one call of `--will-display`. Measured 2026-11-24 on this
Mac, the first `ps` took 0.14 s and the second took 0.17 s. The terminal query
that R-20261125T003234Z#I1 removed from this path was a different cost: it
held the terminal in raw mode and could swallow the keystrokes of the user.
The `ps` call reads no terminal and changes no state.

**The cost is a new review cycle.** This round of the review loop is
record-only. A change to the order of the calls in `report_display_readiness`,
and a test that `ps` does not run, is new code that a review must read. A
fresh review can find a new nit in it. Then a new fix round starts, and the
loop does not end clean.

**The boundary.** This decision settles only the extra `ps` calls of
`--will-display` with a forced protocol. A verdict that reads the transport
wrong is a new finding. A forced path that holds the terminal in raw mode, or
asks the terminal a query, is a new finding.
