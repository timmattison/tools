## `src/nle/src/filters/redaction/stream.rs` `iterm2_value` — no test holds the `=` after the key or the case of the key

**Settled** 2026-11-27 (branch issue-156, finding R-20261127T010505Z#N1)

The finding is accurate for both rules that the doc comment of `iterm2_value`
states:

- **The `=` after the key is not text.** No search in
  `src/nle/src/filters/redaction/tests.rs` matches a `=`. Thus a mutant that
  returns `text.start + key_length..text.end` passes each test. With that
  mutant, a search for `=` turns `ESC ] 1337 ; CurrentDir=/a=b BEL` into
  `CurrentDirX/a=b`.
- **The comparison keeps the case of the key.** Each key in the tests has its
  documented case, for example `File=`. Thus a mutant that compares with
  `eq_ignore_ascii_case` passes each test.

The code is correct. `iterm2_value` returns
`text.start + key_length + 1..text.end`, and it compares the key with
`ITERM2_ENCODED_KEYS` byte for byte. The gap is in the tests, not in the
behavior that a user gets.

The fix costs more than the gap. The branch is in the record-only round of the
review loop. Two new tests are new code that a fresh review must read, and a
nit in that code starts one more fix round. Thus the loop does not end clean.

The boundary: this record settles the tests of these two rules only. A change
to the range or to the key comparison in `iterm2_value` is a new finding. A
search that changes the `=` after a key, or a key in a different case that the
filter reads as an encoded key, is a new occurrence, and it reopens this
decision. Tests of the two rules that a later branch adds close this decision.
