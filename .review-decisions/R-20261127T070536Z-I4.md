## `termstate::TerminalState::take_changed_rows` — no red commit came before commit 2e68ff38d, and the order of the commits stays

**Settled** 2026-11-27 (branch issue-165, finding R-20261127T070536Z#I4)

The finding is correct. Commit `2e68ff38d` added `take_changed_rows` and the
marks of the changed rows, and its guard tests
(`each_change_of_a_cell_marks_its_row`,
`a_move_of_the_cursor_or_a_change_of_the_pen_marks_no_row`), in one commit. The
marks are behavior, and no red commit came before them.

The only fix is a new order of the commits: a red commit before `2e68ff38d`,
then a copy of each later commit. The commits after `1059ba6f1` are not pushed,
thus the fix needs no force push. But it has these costs:

- The branch must move back to `34d995bda`. The git guardrail refuses a hard
  reset, and it has no override. Only Tim can run it, and the review loop runs
  with no person.
- The logs name the old commits. An earlier address-issues run names
  `2e68ff38d` and `3d1d60c70` as the fix commits of its dispositions, and review
  R-20261127T070536Z reviewed `1059ba6f1..4613df091`. The merge gate refuses a
  merge that drops a fix commit that a disposition names. A copy counts only
  when its `git patch-id` is the same. A red and a green in place of
  `2e68ff38d` have a different patch-id, thus the gate refuses until a new
  review runs.
- The rewrite changes no behavior. The guard tests exist and pass, and the
  message of `2e68ff38d` gives three mutants that make them fail. The squash
  merge gives `main` one commit, thus the order of the commits of the branch
  does not go into the history of `main`.

The cost of the fix is thus more than the cost of the defect.

The boundary: this decision covers only the order of `2e68ff38d`. A new commit
on this branch that adds behavior with no red commit before it is a new
occurrence.
