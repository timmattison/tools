# Review decisions

Findings that a review round found **accurate** and that were deliberately not
fixed, because the fix costs more than the defect. `review-time` reads this file
before it reports, so an entry here is out of scope for later reviews.

Reopening is cheap: a real occurrence of the accepted risk reopens a decision. A
new argument about the same hypothetical does not.

## `src/ic` zellij client attribution — argv-scoped, and deliberately incomplete

**Settled** 2026-08-12 (branch ic-mosh-session-scope, finding R-20260812T193340Z#I1)

`zellij_client_pids` attributes a Zellij client to a session by looking for the
session name as a complete argument in the argv of the client. `classify_transport`
then reports Mosh only when *every* client of this session is a Mosh client.

The finding is accurate. `zellij attach` takes an optional `[SESSION_NAME]` and
also accepts `--index <INDEX>`, and a bare `zellij` creates and attaches to a
session with a generated name. A client that starts in one of those forms names no
session in its argv, so it is invisible to the scan. The `all()` rule then runs
over a subset of the clients of this session. When the invisible client is the one
that can show images and a visible client is a Mosh client, `ic` refuses an image
that this session could have displayed.

It is not fixed, because every fix available to us is worse than the defect:

- **Falling back to `ZellijScan::EveryClient` when the list looks incomplete gives
  the same refusal.** `EveryClient` scans every Zellij process on the machine, so
  it finds the Mosh client and answers Mosh. The reasoning changes and the answer
  does not.
- **Counting a viewer that names no session as a client of this session replaces a
  clear error with a silent one.** Such a viewer can belong to a different session.
  When it does, `ic` writes escape sequences that no client of *this* session can
  render, so the image goes nowhere and the user sees no message. Today the user
  gets an error that names Mosh and says to reconnect with `ssh`.
- **Attributing each client through its Zellij socket is correct and costs too
  much.** It resolves every attach form, but it needs `lsof` on every `ic`
  invocation inside Zellij, and `lsof` routinely takes hundreds of milliseconds.
  Linux needs a separate `/proc` implementation. That is a permanent cost on every
  image, paid to close a gap that needs three conditions at once.

The error direction is the conservative one. `ic` refuses and says why, which is
the same answer the code gave before this branch narrowed the scan, and the
refusal is recoverable by naming the session on attach.

**The boundary.** This decision settles the *completeness of argv-based client
attribution*. A finding that proposes widening the argv matching, or that observes
the client set can be partial, is settled here. A refusal observed in the wild
reopens it, as does any finding that this scan is wrong on a client it *can* see.
Findings about this code on a different axis — a bug in the walk, a panic, a
performance problem — are not covered.

## Commit messages on a pushed branch — not rewritten to satisfy a review

**Settled** 2026-08-13 (branch gsw-push, finding R-20260813T173044Z#N1)

The review found that `a83e2ca`, the tip of this branch, is an empty commit whose
message is the single word `test`, where the TDD convention in `CLAUDE.md` calls
for `chore: full pre-commit checks after TDD sequence`. It also observed that the
pre-commit hook here is gated on staged files, so an empty commit runs no gates at
all — the verification that the red/green bargain defers to the end of a run never
happened in that commit.

Both halves of the finding are accurate. Neither is fixed, for different reasons.

**The verification gap is already closed, and not by a commit.** The four gates were
run directly against the tree: `cargo fmt --all -- --check`, `cargo clippy -p gsw
--all-targets`, `cargo machete`, and `cargo test -p gsw`, all green. Running them is
what verification *is*. A commit that re-runs nothing is a record of the run, not the
run, so the record is worth having but is not worth a history rewrite on its own.

**Rewriting the message costs a force-push, and buys nothing durable.** The branch is
published as PR #351, so amending `a83e2ca` makes the local history diverge from
`origin/gsw-push` and the next push needs `--force-with-lease`. Against that: this
repository squash-merges every PR with an explicit `--subject`/`--body`, so no commit
message on this branch reaches `main`. The word `test` is discarded by the merge
either way. Paying a force-push — and the window where a collaborator's fetch
disagrees with the remote — to improve a string that is about to be deleted is the
wrong trade.

**The boundary.** This decision settles *the messages of already-pushed commits on a
squash-merged branch*. A finding that a commit on such a branch is misnamed, or that
its message does not match a convention, is settled here. It does not settle
anything about commit *content*: a commit that is empty when it should carry a
change, or that bundles unrelated work, is a real finding. It does not cover the
squash-merge subject and body themselves, which do reach `main` and are the thing
the convention actually protects. And it does not license skipping verification —
the gates are run, or the finding stands.

## `src/swt/src/create.rs` — the signal window during `git worktree add` stays open

**Settled** 2026-08-14 (branch issue-319, finding R-20260731T182204Z#I3)

`swt create` runs `git worktree add`, and only when that returns does it call
`hold_unverified_worktree`. Nothing is registered as at-risk for the length of the
add, and `anything_at_risk()` is what decides whether a signal becomes a teardown
at all. So a SIGTERM aimed at the `swt` process alone during the add is handed to
the default disposition: `swt` dies, the unshielded `git` child keeps running to
completion, and the run leaves a fully-formed worktree and branch that nothing is
left alive to remove.

The finding is accurate, and it is not a nanosecond race. `git worktree add`
performs a real checkout, so the window is tens of milliseconds to seconds — wide
enough that an orchestrator timing out one of several parallel subagents, which is
the workflow `swt` exists for, is the realistic way to land in it.

**What was fixed.** The narrow sub-window is closed. `hold_unverified_worktree` and
`LockGuard::hold` both used to write their at-risk state and *then* call
`arm_signal_teardown()`, leaving an instant where the registries named something
orphanable and no thread was reading the signals. Both now arm first. That was
free — arming is idempotent, latched behind a `OnceLock`, and inert while nothing
is at risk — so there was no reason not to take it.

**What is not fixed, and why.** The obvious fix for the remaining window is to
register the hold *before* `git worktree add` rather than after. That trades one
failure for a worse one: a signal arriving mid-add would then fire teardown's
`git worktree remove --force` against the same path a live `git worktree add` is
still writing, with no coordination between them. The result is a half-created,
half-deleted worktree and a repository whose `worktrees/` metadata may name a
directory that no longer matches it — a state a user cannot reason about, in place
of one they can. Doing it correctly means teaching teardown to find, signal and
reap the in-flight child before it touches the path, which is a supervisor's worth
of machinery for a window measured in seconds.

**What the accepted consequence actually is.** An orphaned worktree directory plus
its branch, both named after the run that made them, both visible to
`git worktree list`, and both removable by hand with `git worktree remove --force`
and `git branch -D`. Nothing is corrupted and nothing is lost; a run that should
have cleaned up after itself did not. This is also exactly what the TypeScript
original did — it calls `gitMust(worktree add)` and *then* `holdUnverifiedWorktree`
— so the Rust port inherits the behavior rather than introducing it.

**The boundary.** This decision settles *the window between the start of
`git worktree add` and the hold that follows it*. A finding that observes `swt` can
be killed during the add and orphan a worktree, or that proposes moving the hold
before the add, is settled here. It does not settle the arming order inside
`hold_unverified_worktree` or `LockGuard::hold` — that is fixed, and a regression
there is a real finding. It does not cover any *other* unshielded span: a window
opened by new work added between the add and the hold, or by a second git
invocation that creates something before registering it, is new and not covered. An
orphan observed in the wild reopens this, as does any way to make teardown safe
against an in-flight `git worktree add` without a child-process supervisor.

## Commit order on a pushed branch — the test after the block, not before it

**Settled** 2026-08-20 (branch issue-365-followup, finding R-20260820T153740Z#N2)

The review found that the tool-index block of `.husky/pre-commit` landed in `3ff2e53`
and its tests landed in `3a7fc6e`, the commit after it. The TDD rule in `CLAUDE.md`
calls for the failing test first, and a red phase was available here:
`src/repo-guards/tests/pre_commit_hook.rs` already ran the real hook against
throwaway fixtures, so a test of the new trigger could have been written and
committed red. The body of `3ff2e53` says `No test: a hook is configuration, and it
has no runtime behavior the suite can reach`. The body of `3a7fc6e` says that claim
was wrong. The finding is accurate.

It is not fixed, because the defect is the order of two commits and nothing else.

**The coverage is real, and it was verified rather than asserted.** Removing the
block from the hook makes `staged_tool_index_alone_triggers_the_index_guard` fail on
an empty output, and the other three tests of that file still pass. That mutation was
run twice: once by the author, and once by the review, independently. What TDD buys —
a test proven able to fail for the behavioral reason — is present. Only the order in
which the two commits landed is wrong.

**The one fix is a force-push, and it buys nothing durable.** The branch is published
as PR #375, so reordering `3ff2e53` and `3a7fc6e` rewrites already-pushed history and
the next push needs `--force-with-lease`. Against that: this repository squash-merges
every PR with an explicit `--subject` and `--body`, so no commit on this branch
reaches `main`. Both commit messages are discarded by the merge either way. Paying a
force-push, and the window where a collaborator's fetch disagrees with the remote, to
reorder two commits that are about to be deleted is the wrong trade.

**The boundary.** This decision settles *the order of already-pushed commits on a
squash-merged branch*, where the test exists and is mutation-verified by the time the
branch is reviewed. It does not settle a missing test: a change that ships with no
test, or with a test never shown able to fail, is a real finding. It does not settle
the order of commits on an unpushed branch, where a rebase is free. And it does not
license writing implementation first as a habit — the red commit is still the rule,
and this is a record of one branch that broke it and could not cheaply undo it.

## `dirhash` hidden-file count — `.git` is counted, and the note still says `--hidden`

**Settled** 2026-08-29 (branch dirhash-ignore-flags, finding R-20260829T034821Z#I3)

`dirhash` now counts the files the hidden filter removed and names `--hidden` as the
flag that brings them in. On a git clone most of that count is the repository's own
`.git` directory. The shared git directory of this repository holds 1349 files, so a
default run over a normal clone reports about 1349 hidden files and tells the reader
to pass `--hidden`. A reader who does hashes the object store, the index, and the
reflogs. Those differ between two clones of the same commit, so the hash stops
answering the question the README opens with, which is whether two directories hold
identical contents.

The finding is accurate. It is not fixed, because each fix available costs more than
the defect.

- **Dropping `.git` from the count alone destroys the invariant the count exists
  for.** The three walks of `Excluded::measure` partition the excluded files exactly,
  and the count is a promise about what `--hidden` would add. A count that omits
  `.git` while `--hidden` still hashes it under-reports, and the parts stop adding up
  to the whole. That trades a count that is correct and surprising for one that is
  quiet and wrong.
- **Dropping `.git` from the walk as well is a new behavior nobody asked for.** It
  keeps the partition, but `--hidden` then means "include hidden files, except the
  one hidden directory we chose for you", and the help text that says "Include hidden
  files and directories" becomes false. It also removes the only way to hash a `.git`
  directory, which some caller can want. That is a design change for a different
  branch, argued on its own merits.
- **A warning in the note or the README changes no behavior.** The count stays the
  same, the advice stays the same, and the file grows. A reader who is going to pass
  `--hidden` without thinking is not stopped by a sentence.

**What the accepted consequence is.** A default run over a git clone reports a large
hidden count, and a reader who passes `--hidden` gets a hash that covers `.git`. The
count is correct, the advice is honest, and `--hidden` does what its help text says.
The old code hid the same behavior by never counting hidden files at all, which is
the bug this branch fixed.

**The boundary.** This decision settles *whether `.git` belongs in the hidden count
and whether the note must qualify `--hidden`*. A finding that observes the count is
dominated by `.git`, or that asks the note or the README to warn about it, is settled
here. It does not settle the arithmetic: a count that double-counts, that disagrees
with what the flag actually adds, or that fails to partition the excluded files is a
real finding. It does not settle a deliberate proposal to change what `--hidden`
means, which is a design question and not a review finding. A user who reports a
surprising hash because of this reopens it.

## `src/wn/src/graph.rs` — a doubled hyphen with a space on each side, inside the prose of a port

**Settled** 2026-09-03 (branch issue-418, finding R-20260903T152228Z#I3)

`Grid::sides_at` reads an ASCII spelling as a wire only when a neighbor on a
side it touches draws a wire as well. `Grid::run_ends_at_a_letter` then takes
that wire back out when the run it stands in ends at a letter, because a run of
hyphens that touches a word is a word. The end test reads the first cell of the
run that draws no wire and asks whether it is a letter.

The finding is accurate. A space is no letter, so a run with a space at each
end keeps its wire, and the spaced `--` a reader writes for an em-dash draws
one.

**What was fixed.** An ASCII wire whose run ends at a letter draws nothing, so
`#249  (pass --hidden)`, `#249  (a 30-line window)`, and
`#249  (the gallery--the last one)` all read. Each of the three was pasted into
the picture of the two streams that join and run through the binary, and each
one gives the rows the picture with the plain label gives.

**What is not fixed.** `#249  (the gallery -- the last one)` refuses, and the
message reads `"#249  (the gallery" stands beside a wire and is not a step`.
The run of that `--` holds a space at each end, no letter stands at either end,
and the rule keeps the wire.

**Why it is not fixed.** The fix on offer is an end test that walks past the
spaces before it reads the character. It was written and run: the spaced label
reads, and every test of `wn` stays green, because no test draws the picture
that pays for it. That picture is `A --> #4`, the ASCII spelling of the one the
test `a_label_beside_a_wire_is_not_a_step` draws with the box-drawing set.
Today

```text
A --> #4 --+
#5 --------+--> #6
```

earns `NotAStep("A")`, which names the label alone and keeps the edge from `A`
to `#4`. With the space-skipping test the wire of `A --> #4` draws nothing, the
whole text reads as one port, and the message becomes `NotAStep("A --> #4")`.
The edge leaves the graph, and the message names an arrow the reader drew as
though the reader wrote it as prose. Both texts refuse, and the second refusal
stops naming the fault: a reader who is told `A` closes up the label, and a
reader who is told `A --> #4` is told that their arrow is text. The module
refuses rather than guesses everywhere else, because a guess sends somebody to
the wrong issue, so trading a refusal that names the fault for one that hides
it is the wrong direction.

**What the accepted consequence is.** A label that writes an em-dash as a
spaced `--` refuses, and the message names the text it cut at. A reader closes
up the hyphens, or writes the em-dash itself, and the picture reads.

**The boundary.** This decision settles *an ASCII wire run whose ends are
spaces, inside the prose of a port*. A finding that asks the end test to walk
past the spaces is settled here. It does not settle the run rule itself: a run
that ends at a letter and still draws a wire, or a run that ends at a digit and
stops drawing one, is a real finding. It does not cover the box-drawing
spellings, which never stand inside a word. A reader who reports a picture this
refuses reopens it, as does a rule that parts the spaced `--` of a label from
the spaced `-->` of a wire and keeps every picture the tests draw.
